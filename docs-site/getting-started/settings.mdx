---
title: "Settings"
description: "Tune supported runtime controls from the open·kritt UI."
---

Open **Settings** under **Configure** to view and edit supported, non-secret runtime
controls. The page shows the configured value, its source, its accepted range,
and whether that value is live or needs an engine container recreation.

## Available controls

| Setting | Applies | Purpose |
| --- | --- | --- |
| Engine worker slots | Live | Aggregate capacity shared by scan workflow and post-processing jobs. Set it to `0` to pause pickup of new work. |
| Concurrent scan pool | Live | Maximum number of immediately started scans admitted at once. Queued scans wait until the active pool is empty. |
| Workers per scan | Live | Hard cap on worker slots used by one scan. Set it to `0` for automatic fair sharing. |
| Autoscale on provider capacity | Live | Reduces a scan's future worker cap after the provider reports server-capacity throttling. It does not change account quota limits. |
| Minimum free storage | Live | Pauses new scan containers below the configured host free-space floor. |
| Ignore low-storage safeguard | Live | Starts new scan containers regardless of free disk space while preserving the configured threshold for later use. |
| Workspace setup concurrency | Engine recreation | Limits simultaneous checkout and isolated workspace preparation. |
| Model-call retries | Live | Additional attempts for retryable workflow-step and post-script model calls. |
| Cyber-block retries | Live | Opt-in additional attempts after a provider blocks a request under its cybersecurity safety policy. `0` keeps the fail-fast default. |
| Auto-resume failed scans | Live | Resumes every scan that has remained failed for about one second, continuing from its completed work. Disabled by default. |
| Model-call timeout | Live | Maximum duration of each future harness invocation. |

Live changes affect future work; already-running model calls keep the values they
started with. In the bundled Docker Compose deployment, settings are also written to
the project `.env` file so a future `docker compose up` recreation keeps them.

<Note>
  `docker compose restart` does not reload values from `.env`. After changing workspace
  setup concurrency, recreate the engine with
  `docker compose up -d --force-recreate engine`.
</Note>

<Warning>
  Raising worker or setup concurrency can exhaust provider rate limits, Docker
  networking, CPU, memory, or disk capacity. Ignoring the low-storage safeguard can
  fill the host disk and cause scans or other services to fail. Auto-resume can retry a
  persistent failure repeatedly and consume provider quota. The UI asks for confirmation
  before enabling the storage override, pausing work, or raising worker slots above the
  conservative recommendation.
</Warning>

## Scheduling behavior

Engine worker slots are shared execution capacity. The concurrent scan pool controls how
many scans can share that capacity, while workers per scan prevents one scan from taking
every slot. With automatic sharing, active scans receive a fair portion of the available
workers.

Queued scans remain separate from that pool: they start only after active scans finish.

**Auto-resume failed scans** is off by default. When enabled, the backend checks twice
per second and moves every scan that has remained failed for about one second back to
pending so the engine can continue from its completed work. This happens without an open
browser or a **Resume** button click. When the setting is disabled, failed scans remain
failed until you use the manual **Resume** action. Paused and stopped scans always remain
manual.

Model-call retries happen before a scan reaches the failed state and are independent of
whole-scan auto-resume. Temporary provider limits use the separate `rate_limited` state
and their own automatic retry schedule.

Cyber-block retries are independent of ordinary model-call retries. A value of `3`
allows three retries after the first blocked call, for up to four total attempts.
Because policy decisions are often deterministic, leave this at `0` unless repeated
attempts are appropriate for your provider account and workload.

## Secrets

Settings returns only an explicit allowlist of non-secret runtime values. Provider API
keys and login credentials are managed separately under **Accounts** and are never
included in the settings response.
